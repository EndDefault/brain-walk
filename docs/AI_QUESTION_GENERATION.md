# 도구를 사용하는 맞춤 출제 AI 정의

2026-10-01 결과: 공통 모델의 추가 학습과 분리 평가를 수행했습니다. 현재 후보는 약한 유형 판단이 기준에 미달하여 제품 배포는 보류합니다. 이후 사용자는 **AI 출제·도전·개인 최고 기록 갱신**을 게임의 중심으로 정하고, 결과 화면에서 다음 문제를 미리 준비하는 방식을 제안했습니다. 다음 작업은 보관 모델의 Android 실행 검증과 시연 연결을 우선합니다. 아직 앱 생성 연동·미리 생성·최고 기록 기능은 구현하지 않았습니다. 실제 측정과 제외 후보는 [추가 학습 결과](QUESTION_MODEL_REPORT.md), 다른 PC에서 이어서 할 내용은 [인계 메모](QUESTION_MODEL_HANDOFF.md)에 기록합니다. 아래 역할 정의는 구현 목표이며 달성한 성능을 뜻하지 않습니다.

2026-09-30 · **생성 모델을 배포 전에 공통 출제 능력으로 보정하는 실험을 추가했습니다. Android 앱 연결은 아직 없습니다.** 현재 앱에서 실행되는 것은 `ProblemGenerator`의 무작위 출제와 [밴딧 난이도 선택](AI_DESIGN.md)입니다. 학습·평가 방법은 [공통 모델 보정 실험](../training/question_author/README.md)에 기록합니다. 학습 산출물과 앱에서 실제 사용되는 기능을 구분합니다.

## 맡길 일

**AI는 최근 수행 기록을 읽고 앱이 제공한 색·그림·숫자 재료와 출제 도구를 이용해 다음 10문제의 기억 대상과 오답 보기를 구성한다. 앱은 그 구성을 검증한 뒤 게임으로 보여 준다.**

예를 들어 최근 특정 색 조합을 자주 혼동했다면 그 조합을 일부 다시 연습하도록 제안하고, 직전 문제의 반복은 줄이면서 다른 재료도 섞습니다. 숫자 자리 교환처럼 어떤 보기가 혼동 원인인지 관찰할 수 있는 구성을 제안할 수도 있습니다. 이 예시는 출제 의도이며 실제 개인화 효과는 비교 실험으로 확인해야 합니다.

그림 파일·폰트·정답 판정 자체를 모델이 새로 만들지 않습니다. 시니어는 기존과 같이 큰 보기를 눌러 답합니다. 글씨 쓰기나 음성 입력은 필요하지 않습니다. 새로운 UI 문구도 모델의 자유 생성에 맡기지 않습니다.

## 역할 분담

| 역할 | 담당 | 상태 |
| --- | --- | --- |
| 10문제 합산 성적에 따른 공통 난이도 선택 | 기존 규칙 + Discounted UCB 밴딧 | 구현됨 |
| 같은 조건 안에서 기억 대상·오답 보기 구성 | 기기에 탑재할 생성 모델 | PC 보정·생성 평가 완료, Android 미연결 |
| 재료 목록·조건 제한·정답 계산·타이머·채점 | 앱의 결정적 코드 | 기존 기능을 재사용/확장 예정 |
| 출제안 검증·저장·실패 시 대체 출제 | 앱 | 검증 연결과 저장 확장 예정 |

AI가 할 수 있는 구성은 규칙으로도 상당 부분 구현할 수 있습니다. 생성 모델을 쓰는 이유는 여러 기록을 함께 해석해 구성을 제안하도록 하기 위함이며, 모델을 넣었다는 사실만으로 무작위/규칙 출제보다 낫다고 보지 않습니다. 반복률·오답 재방문·개인별 적합성과 대기 시간을 비교해 추가 가치가 있는지 판단합니다.

최근 기록을 입력으로 주는 **추론**과 모델 가중치를 다시 훈련하는 **학습**을 구분합니다. 최신 사용자 요청에 따라 배포 전에 사전 학습 모델을 여러 사용자 상황으로 추가 보정합니다. 실제 사용자 자료가 없으므로 첫 실험은 직접 작성한 가상 상황을 사용하며, 개인 한 명의 기록이나 개인 밴딧 학습값을 배포 모델에 넣지 않습니다. 설치 후에는 공통 모델에 각 기기의 개인 기록을 입력합니다. 사용자의 플레이마다 생성 모델의 가중치를 갱신하지 않으며, 기존 밴딧의 보상 학습은 별도로 유지합니다.

## 입력과 제공 도구

앱이 요청마다 같은 게임의 조건 스냅샷과 슬롯 계획을 고정합니다. 종합 10문제의 4/3/3 순환, 순서 섞기, 세 유형 공통 난이도, 연습 제외 원칙을 유지합니다. 모델은 유형 비율·보기 수·기억/대기/풀이 제한을 변경할 권한이 없습니다.

입력은 익명 기기 내부 기록의 제한된 요약입니다. 유형·기억 대상·오답 선택·첫 선택/최종 정답·걸린 시간·적용 조건·중단 여부·최근 노출 빈도를 포함합니다. 비교 가능한 조건끼리 집계하며 연습/중단 기록을 정식 성공·실패로 섞지 않습니다. 기록이 없는 처음에는 전체 재료에 고르게 노출하는 구성을 요청합니다.

아래 이름은 **Android 연결 예정 계약**입니다. Python 학습 실험에는 `submit_question_plan`의 형식·허용 재료 검증과 출력 제한을 구현했고, 기록/재료는 요청 입력으로 제공합니다. 앱의 도구 호출 함수는 아직 구현하지 않았습니다.

| 도구 | 입력 → 결과 | 권한 |
| --- | --- | --- |
| `get_training_context` | 요청 ID → 고정 조건·10개 슬롯·최근 유효 기록 요약 | 읽기 전용. DB 전체/개인 식별 정보 접근 없음 |
| `list_materials` | 유형 → 허용 ID와 표시 정보·객관적 속성 | 읽기 전용. 앱에 포함된 재료만 반환 |
| `validate_question_plan` | 10개 슬롯의 대상 ID·오답 ID·출제 의도 코드 → 검증 결과·오류 코드 | 메모리 안에서 검사. 파일·기록·게임 상태 변경 없음 |
| `submit_question_plan` | 요청 ID와 출제안 → 최종 검증 결과 | 앱에 제안만 전달. 저장과 적용은 앱이 결정 |

예시: 앱이 `NUMBER`, 보기 4개로 지정한 슬롯에 모델이 `targetId="number:42"`, `distractorIds=["number:24","number:41","number:43"]`, `reasonCode="REVIEW_CONFUSION"`를 제안합니다. 이 ID 체계도 설계 예시입니다. 앱이 카탈로그에서 숫자 42를 찾아 정답으로 지정하고 보기 순서를 직접 섞습니다. 모델이 정답 인덱스나 화면에 표시할 숫자를 임의로 적도록 하지 않습니다.

원재료는 현재 `ProblemGenerator`가 사용하는 색 좌우 조합, `PictureSymbol` 16종, 두 자리 숫자 10~99입니다. 먼저 이 목록을 읽기 전용 공용 카탈로그로 추출해야 합니다. 필기 인식·새 이미지 생성·외부 자료 검색은 이 계약에 포함하지 않습니다.

## 그대로 믿지 않고 확인할 것

출력 JSON의 모양이 맞아도 내용이 맞는지는 별도 문제입니다. 앱은 모델 응답마다 다음 항목을 검사합니다.

1. 허용된 도구 이름·키·자료형·길이만 받고, 출력 크기와 도구 호출 횟수를 제한합니다. 다른 파일/네트워크/셸 도구는 제공하지 않습니다.
2. 요청 ID·조건 버전과 정확히 10개 슬롯이 일치해야 합니다. 슬롯 누락·중복·유형 변경·임의 난이도 변경을 거절합니다.
3. 모든 대상/오답 ID가 해당 유형의 카탈로그에 있어야 합니다. 보기 수는 고정 조건과 같고, 보기 콘텐츠는 서로 달라야 하며 정답은 정확히 하나여야 합니다.
4. 정답과 보기 순서·문제 ID·생성 시각은 앱이 만듭니다. 기존 `MemoryProblem` 불변식도 마지막에 다시 적용합니다.
5. 재개 시에는 중단된 현재 대상과 다른 재료를 사용합니다. 재료가 부족한 유형에서 중복 금지 규칙 때문에 출제 불가능해지지 않도록 게임 내 반복 최소화는 품질 지표로 평가합니다.
6. 출제 의도는 허용 코드로 저장하되 사실로 간주하지 않습니다. 모델의 설명을 정답/난이도/인지 향상 증거로 사용하지 않습니다.

검증 오류는 제한된 횟수 안에서 수정 요청합니다. 총 생성 시간, 토큰, 호출 수, 재시도 상한은 대상 태블릿 측정 후 설정값으로 고정합니다. 모델 로딩 실패·시간 초과·잘못된 출제안·메모리 부족에서는 기존 무작위 생성기로 전환하고 게임을 계속할 수 있게 합니다. **대체 문제를 AI 생성 성공으로 기록하지 않습니다.** 모델 실패는 저장 실패와 별도로 처리합니다.

처음에는 보수적으로 10문제 계획 전체가 유효한 경우에만 채택합니다. 일부만 유효하면 상한 안에서 계획을 수정하거나 전체 계획을 기존 생성기로 대체합니다. 사용자에게 내부 검증 오류를 길게 노출하지 않고 준비 상태와 다시 시도/기본 문제로 시작할 수 있는 흐름을 제공합니다.

## 저장과 실행 경계

게임 시작 전에 백그라운드에서 출제안을 준비·검증합니다. 추론을 메인 스레드, 타이머 진행 구간, Room 트랜잭션 안에서 실행하지 않습니다. 검증이 끝난 계획과 고정 조건은 원자적으로 저장하고 첫 기억 화면부터 기존 게임 엔진을 사용합니다. 사용자가 시작을 취소하면 준비 작업을 취소하고 늦게 도착한 응답은 요청 ID로 폐기합니다.

### 결과 화면에서 다음 게임 미리 준비 — 구현 예정

완료한 게임의 성적 저장과 다음 공통 난이도 결정이 커밋된 뒤 다음 10개 슬롯 계획을 확정하고, 결과 화면을 보는 동안 별도 작업으로 생성합니다. 결과 화면 진입 자체를 생성 완료까지 지연하지 않습니다. 이 시점에는 다음 게임을 진행 중으로 등록하거나 플레이 시간·학습 보상을 계산하지 않습니다.

- 준비 요청은 완료 게임 ID·조건 버전·모델/계약 버전으로 구분하고, 한 번에 다음 게임 한 묶음만 준비합니다. 화면 재진입으로 중복 실행하지 않습니다.
- 생성한 계획을 검증한 뒤 준비 상태로 저장합니다. ‘다시 도전’에서 조건이 여전히 같은지 검사하고, 한 게임에만 원자적으로 연결합니다. 준비된 내용을 새로 생성하지 않습니다.
- 사용자가 준비보다 먼저 시작하면 준비 안내를 표시합니다. 측정 후 정한 시간 상한을 넘거나 실패하면 기존 출제로 진행하고 출처를 구분합니다. 첫 게임은 준비된 계획이 없으므로 별도 생성 시간이 필요합니다.
- 조건·모델·입력 기록이 달라지면 오래된 계획을 적용하지 않습니다. 취소되거나 대체 출제로 이미 시작한 요청의 늦은 응답은 폐기합니다.
- 저장을 마친 준비 계획은 앱 재시작 후 조건을 확인해 재사용할 수 있습니다. 앱 종료 후에도 생성이 계속된다고 가정하지 않으며, 미완료 요청은 다음 진입에서 복구·재요청합니다.

이 방식은 결과 확인 시간을 활용해 대기를 줄이는 설계입니다. 태블릿 생성 속도·메모리 문제 자체를 해결하거나 항상 즉시 시작을 보장하는 기능은 아닙니다. 개인 최고 기록은 완료한 게임의 실제 성적과 비교 가능한 난이도 조건으로 계산하며, 모델의 약점 분류나 설명을 점수로 사용하지 않습니다. 구체적인 점수 공식·화면은 후속 구현에서 정합니다.

생성 경로(`MODEL`/`RULE_FALLBACK`/`RULE_PRACTICE`), 모델·프롬프트·도구·카탈로그·검증기 버전, 적용된 계획, 출제 의도 코드, 생성 시간, 검증/대체 사유를 저장합니다. 개인 기록이나 모델 입력 전문을 진단 로그/GitHub로 내보내지 않습니다.

재시작은 저장된 계획과 완료 기록을 복구합니다. 완료한 문제를 새로 만들거나 다시 채점하지 않습니다. 중단된 한 문항은 같은 슬롯·유형·조건의 새 대상으로 교체하고, 생성이 늦거나 실패하면 그 슬롯만 검증된 대체 문제를 사용해 교체 이력을 남깁니다. 기존 난이도 학습의 `generatorVersion` 적격성 검사는 생성 출처와 콘텐츠 호환 버전을 구분하도록 함께 개정해야 합니다. 모델을 바꿀 때 비교 실험/보상 연결을 어떻게 구분할지도 버전과 함께 기록합니다.

## 구현 전 결정과 검증

- 실제 태블릿 모델·RAM·허용 설치 용량을 확인하고 모델 로딩, 초기/반복 생성 시간, 최대 메모리, 발열, 완전 오프라인 동작을 측정합니다. 현재는 특정 기기에서 실행 가능하다고 확정하지 않았습니다.
- 런타임과 모델 가중치의 라이선스를 각각 확인합니다. 사용자 허용 목록과 필요한 저작권·LICENSE·NOTICE 조건을 충족하는 후보를 선택합니다. 런타임 라이선스가 허용된다고 모델 가중치까지 같은 조건인 것은 아닙니다.
- 기록 없음/같은 보기 반복 오답/느린 정답/부분 중단/손상된 응답/없는 ID/도구 오용/시간 초과/재시작 사례를 검증합니다. 잘못된 문제는 표시하지 않아야 합니다.
- 무작위·간단한 규칙·모델 출제를 **같은 조건**에서 비교합니다. 검증 통과율·대체 비율·중복률·기록에 따른 구성 변화·지연을 먼저 평가합니다. 더 높은 정답률만으로 개인화 효과나 인지 향상을 주장하지 않습니다. 생성 실패를 제외해 성공률을 부풀리지 않습니다.
- 현재 밴딧은 조건 변화의 결과를 보상으로 받으므로 출제 구성 변화도 점수에 영향을 줄 수 있습니다. 출제 방식과 버전을 기록하고, 모델 출제의 추가 가치는 난이도 조건을 고정한 비교부터 확인합니다.

초기 순서는 가상 사용자 자료와 출제 계약 → 개발 PC에서 공통 모델 보정·분리 평가 → 카탈로그/생성기 인터페이스 분리 → Android 검증기·실패 처리와 모델 실행 → 계획/출처 저장 마이그레이션 → 화면 연결·기기 검증입니다. 외부 AI API 계정은 사용하지 않습니다. 가상 자료에서 출제 규칙을 잘 지킨 결과만으로 실제 사용자에게 적절하다고 확정하지 않습니다.
